# Emergent Language Lab

A local experiment app for two independent conversational agents powered by your downloaded Ollama model. Run both agents on one computer, or connect two computers so each generates its own agent's messages. The browser dashboard, inference, and experiment records run on your machines. Nothing is published or deployed.

The default model is `gpt-oss:20b`. Python 3.10 or newer is required; the application uses the Python standard library and has no package installation step.

## Start on this computer

Make sure Ollama is running and the model is available:

```sh
ollama list
```

If Ollama is not running, open the Ollama app or run `ollama serve` in another terminal. If this is a new computer without the model, download it with `ollama pull gpt-oss:20b`.

From this directory:

```sh
python3 app.py --open
```

On this Mac, you can also double-click `Launch.command` in Finder. Keep its terminal window open while using the app.

Open <http://127.0.0.1:8765> if the browser does not open automatically. The app starts with **Self-conversation**, **Open dialogue**, and compression off. Select a topic preset or edit the topic, then start a run. Agent A and Agent B use the same model weights with separate role-specific prompts; this is two agent contexts, rather than a second copy of the model in memory.

The local dashboard only listens on the loopback interface. Closing the browser does not stop a run while the Python process remains open. Use the dashboard's stop control to finish a run, and Ctrl+C in the terminal to stop the app. Runs interrupted by an app restart are preserved but do not automatically resume.

## Connect two computers

Put a copy of this app on both computers and make sure both have Python, a running Ollama service, and `gpt-oss:20b`. Connect them over a trusted LAN or private VPN. The second computer runs the app's authenticated peer listener; Ollama itself can stay bound to its usual `127.0.0.1:11434` address.

1. On **computer B**, run:

   ```sh
   python3 app.py --peer-listen 0.0.0.0 --peer-port 8766 --open
   ```

2. In B's local dashboard, find the peer connection details and reveal/copy its token. Note B's LAN address; its peer URL will look like `http://192.168.1.25:8766`. Allow the Python app's peer port through the computer's firewall if prompted.

3. On **computer A**, run:

   ```sh
   python3 app.py --open
   ```

4. In A's dashboard, choose **Two computers**, enter B's peer URL and token, then test the connection and start a run.

A coordinates the experiment. Turns assigned to Agent A are generated by A's Ollama, and turns assigned to Agent B are generated by B's Ollama. Replies travel back to A and become the other agent's conversation context. B's dashboard shows incoming worker activity. Do not start a second coordinating run on B for this pairing.

The peer token is stored in B's `data/peer-token` and reused after a restart. Keep it private. The peer listener serves model requests, while the dashboard remains local. Plain `http://` pairing is intended for a trusted LAN or private VPN; use a secure tunnel for connections across untrusted networks. Do not forward Ollama's port to the internet.

The remote computer uses its own launch-time model setting. For example, if both computers have your custom 32K tag:

```sh
python3 app.py --model gpt-oss:20b-32k
```

Use `python3 app.py --help` for port, storage, and Ollama URL settings. To test transport on a single computer, run B with a different dashboard port and a separate data directory:

```sh
python3 app.py --port 8767 --data-dir data-peer-test --peer-listen 127.0.0.1 --peer-port 8766
```

Then point A to `http://127.0.0.1:8766`. This checks the client/server path; it does not verify another computer's network or firewall.

## Experiments

### Open dialogue (default)

Agents alternate on a topic or opening message you choose. The default topic is:

> Develop a reliable, concise way to cooperate using whatever text-based method is most efficient.

The editable topic presets include cooperation, music, movies, joke-telling, flirting, storytelling, philosophy, and science. Select a preset to fill the topic field, then change its text freely. The opening-message field can give Agent A a more specific starting point.

Open dialogue has no task accuracy measure. Compression starts off, so the word budget stays constant throughout the run; you can enable compression when you want it to shrink. The word budget and recent-history window still constrain the exchange.

### Cooperative coordination

Each round has a sender and receiver, with roles swapped in the next round. The sender sees a private target: an ordered pair of objects described by English features. The receiver sees four candidate pairs, but not the private target. The sender must describe the target so the receiver can identify the correct candidate. The receiver ends its answer with a standalone line such as `Choice: 2`.

Both agents receive objective success/failure feedback. A word limit applies to actual messages relayed between them. When compression is enabled, that limit shrinks from the configured starting budget to six whitespace-separated words during the run, encouraging more compact conventions while the task still rewards successful understanding. The receiver's `Choice: N` line counts toward that budget. The task repeats with new combinations so conventions can be reused. Only the agents' final messages and public feedback are shared between agent contexts; private task prompts and model reasoning are not relayed.

## Conditions and interpretation

The prompts ask for English and allow mutually understood English shorthand. English is a prompt-level requirement, not an automatic language classifier. Review the transcript to assess whether the agents remain understandable. A shrinking message budget may also cause invalid choices or failed tasks; those failures are part of the record. The cap counts whitespace-separated words: long compounds or punctuation can pack more information into one word, so this is a practical constraint rather than a strict information-theoretic channel capacity.

These are fixed pretrained models. Any convention develops within the supplied conversation context; the application does not update model weights, train agents, or guarantee the discovery of a new language. Private observations, repeated cooperation, feedback, and a communication bottleneck are useful experimental conditions, not proof of emergence. The design is inspired by [cooperative emergent communication research](https://arxiv.org/abs/1804.03980) and [referential communication games](https://arxiv.org/abs/2106.02668); it does not reproduce those papers' reinforcement-learning experiments.

For a useful comparison, keep the model, task seed, turn count, and sampling settings fixed while changing one condition:

- Compare compression enabled with the default constant word budget.
- Increase the word budget to reduce communication pressure.
- Reduce the recent-history window to test dependence on remembered conventions.
- Compare task performance early and late in the transcript, checking whether shorter messages still communicate the private target correctly.

Accuracy, mean word count, lexical diversity, and repeated messages are descriptive measurements. There are four candidates, so random selection has a 25% chance baseline. Lower lexical diversity alone can indicate repetition or failure; it does not establish a new protocol. Stronger claims need controlled comparisons, multiple seeds, and tests with new tasks or partners. The seed makes task generation repeatable and is passed to inference; it does not promise identical model output across hardware, Ollama versions, or scheduling.

## Model settings and records

The dashboard exposes temperature, top-p, inference seed, reasoning level, context size, generation token cap, word budget, history window, and turn count. The defaults use `think: high`, GPT-OSS's highest supported reasoning effort, with a 32,768-token context and an 8,192-token generation cap shared by reasoning and the final answer. The context reserves room for the larger generation budget and the conversation prompts. Replies may take substantially longer with these settings. Each model request can run for up to two hours by default; adjust this with `--generation-timeout`. The visible message budget stays at 80 words unless you change it; private reasoning does not count against that word budget.

The Ollama integration follows the [chat API](https://docs.ollama.com/api/chat) and keeps [thinking output](https://docs.ollama.com/capabilities/thinking) separate from the final response. Reasoning traces are neither shown to the other agent nor saved in run records.

The history window is an upper limit. Before inference, the app may remove older public history to reserve space for generation and a 1,024-token safety allowance. It estimates tokens from UTF-8 bytes because this API does not supply a preflight tokenizer. The estimate is conservative for ordinary English, but cannot guarantee that arbitrary text fits. Current system instructions and task observations are preserved; a task that still exceeds the estimate produces an error. JSON records include the estimate and number of history messages dropped.

Completed turns are saved under `data/runs/`. Export JSON for settings, task prompts, messages, feedback, and generation metadata, or Markdown for a readable transcript. Exact private prompts are included in human-facing exports for auditability; keep those files separate from any future agent input. Peer tokens are excluded from run records and exports. Do not treat the data directory as source code or share it without reviewing its contents.

## Verification and troubleshooting

Run model-free checks with:

```sh
python3 -m unittest discover -s tests -v
```

The suite includes real HTTP tests on temporary loopback ports with fake model responses. It requires permission to open local sockets, and does not download or invoke a model.

For an optional check against your running Ollama model, run:

```sh
python3 scripts/verify_local.py
```

This makes two self-conversation calls and four network-mode calls using two temporary local app instances. It checks real inference, turn routing, archives, and exports without keeping verification runs. Both instances use this computer, so it does not verify a second physical computer's network or firewall. It uses the current high-reasoning defaults and can take a long time, with the same model memory as a normal run. Use `--model` or `--ollama-url` to select a different already downloaded model or endpoint.

If Ollama is unavailable, check `ollama list` and the dashboard's Ollama status. The standard Ollama address is `http://127.0.0.1:11434`; set `--ollama-url` when your installation uses another local endpoint.

If pairing fails, test B's peer URL and token from A, check both machines are on the same reachable network, and confirm the firewall permits B's peer port. A `127.0.0.1` address always means the computer making the request; use B's LAN/VPN address from A.

For faster comparisons, use fewer turns or select a lower reasoning effort in Model & memory settings. Pause takes effect at a turn boundary; stopping prevents a late response from becoming another completed turn. Check run status and any displayed error before starting a replacement run.
